# Insiculous 2D — Editor UI/UX Audit & Roadmap

**Date:** 2026-08-27
**Basis:** full read of `crates/editor` + `crates/editor_integration` at HEAD, plus six live screenshots of the Pong and Editor Demo instances taken 2026-08-27 08:17–08:29.
**Purpose:** input for a Claude Code planning session. Every item has a file:line anchor, an observable symptom, and a concrete fix.

> **Note on `examples/pong_editor_screenshot.png`:** it is stale. It renders `"(Asset browser not yet implemented)"`, a string that no longer exists in the tree. Don't plan against it. The 2026-08-27 screenshots are ground truth, and they show real progress: semantic entity names, a working asset browser, 60 FPS.

## 0. Vocabulary

The point of this section: names for things that currently feel wrong but resist description. Use these terms in Claude Code prompts — they're precise enough to plan against.

| Term | What it means here |
|---|---|
| **Elevation model** | A deliberate ladder of surface brightnesses (window → panel → header → input → popup) so containment is visible without borders. The editor has no ladder: adjacent surfaces differ by <1.5:1, so panels have no edges. |
| **Affordance** | The visual promise that something is interactive. Splitters have no resize cursor, entities have no selection outline, `[X]` has no tooltip — the editor makes almost no promises. |
| **Selection affordance** | Specifically: viewport feedback that an entity is selected. There is none unless the entity has a Collider. |
| **Z-band / layer model** | An explicit stacking order for chrome. The editor has one implicit band (statement order in `EditorGame::update`) plus a single `begin_overlay` escape hatch used twice. Everything else is "whoever draws last wins". |
| **Wiring gap** | A subsystem that is written, tested, and never called from the frame loop. `grid.rs` (489 lines, 9 tests, zero production callers) is the canonical case. |
| **Dead token** | A theme/layout constant that exists, is documented, and is never read. `play_green`, `TOOLBAR_HEIGHT`, `slider_height`, `bg_viewport`. |
| **Closed-world registry** | A compile-time `match` over a fixed component list, generated by macro. Excellent for a fixed set; structurally unable to accept a downstream game crate's types. You have four of these for one concept. |
| **Silent hole** | A world mutation that bypasses the command system, so undo appears to work and quietly doesn't. |
| **Dirty desync** | Undo history and save state disagreeing about whether work exists. Inspector edits push commands but never `mark_dirty()`. |
| **Chrome bleed** | Game UI drawing outside the viewport, onto editor chrome. Visible in three of six screenshots. |
| **Label collision** | An inspector row where the field label and its input box overlap because label width is a fixed magic number. |
| **Fake header** | A sub-property rendered with the component-header style (`"  Type: Dynamic"`), so it reads as a component. |
| **Read-only island** | A component the inspector can display but not edit. Five of fourteen. |
| **Phantom multi-select** | A selection model that is genuinely multi, with every consumer reading `primary()` only. |
| **The seam** | (§5) The stable, serializable identity for a chunk of game logic that lets the editor show and tune it without knowing its Rust type. This is the whole end-state question in one word. |

## 1. P0 — Broken. Fix before anything cosmetic.

### 1.1 Clicking a toolbar button silently reselects whatever sprite is underneath it

> **Confirmed by repro, 2026-08-27.** Selecting in the hierarchy and switching tools with Q/W/E/R works correctly. Clicking a toolbar button deselects the current object and **selects the Background instead.**

The toolbar floats **inside** the scene-view rect (`toolbar.rs:176`), and viewport picking only guards against menu overlays:

```rust
// editor_game/viewport_interaction.rs:40
if ctx.ui.is_input_blocked_at(ctx.ui.mouse_pos()) { return; }
```

`is_input_blocked_at` is fed only by `ui.begin_overlay`, used in exactly two places. Toolbar buttons are ordinary widgets. The toolbar renders at step 4 of `EditorGame::update`, picking runs at step 6, and press+release both land inside `viewport_bounds` — so picking runs against the toolbar's own screen position:

```rust
// viewport_interaction.rs:55-73
if input_result.clicked {
    let pickables = build_pickable_entities(ctx.world);
    let pick_result = self.editor.picker.pick_at_screen_pos(..., input_result.click_position, ...);
    if let Some(entity_id) = pick_result.topmost() {
        ...
        self.editor.selection.select(entity_id);      // ← the observed bug
    } else if !input_result.shift_held && !input_result.ctrl_held {
        self.editor.selection.clear();
    }
}
```

**The pick doesn't miss — it hits.** Pong's `Background` sprite spans the whole scene, so it is under the toolbar, so `topmost()` returns it and `select()` replaces your selection with the Background. In a scene with nothing under the toolbar you'd get the `clear()` branch instead. Same for Play/Pause/Stop.

**This is worse than a plain deselect**, and it's why it's confusing rather than merely annoying: the inspector immediately refills with a *different, valid-looking* entity. Nothing announces the swap. Edit a field expecting your paddle and you've edited the background.

**Fix:** give `UIContext` a per-frame "mouse consumed by a widget" flag set by `interact` when `state == Active`; bail on it in `handle_viewport_picking`. Interim: subtract `toolbar.bounds() ∪ play_controls.bounds()` from the pickable region before the `clicked` branch. The real fix is §5.4's layer model — chrome-over-viewport hit arbitration should be a property of the UI layer, not a special case per call site.

### 1.2 Play → Stop permanently deletes components the engine doesn't enumerate

```rust
// world_snapshot.rs:7-8
// Known limitation: Custom component types not in the known list are lost on restore.
```

`restore` calls `world.clear()` (`:120`) then rebuilds from 18 hardcoded `Option<T>` fields (`:19-46`). Anything else is gone — not un-restored, **destroyed**.

Concretely: `examples/editor_demo.rs:194-198` attaches `HierarchicalStateMachine<PlayerState, PlayerGroup>` to the player. The first Play→Stop cycle silently deletes it. `Tilemap` is in the editor registry (`stored_component.rs:322`) but absent from `EntitySnapshot` — a *first-party* type erased by the Play button.

For an engine whose pitch is "build 2D games", the first custom component a user writes is annihilated by Play.

**Fix (staged):** immediately, add `Tilemap` to `EntitySnapshot` and make `capture` log-and-refuse on unknown types rather than dropping them. Properly, replace the hand-maintained list with `capture_all_components`/`restore_components` (`stored_component.rs:178, 336`), preserving the deliberate Parent/Children exclusion (`:176-177`) explicitly instead of via two divergent lists.

### 1.3 `Save` and `Save As` are unguarded during Play

Every neighbouring menu arm has `if !self.editor.is_playing()`. These two don't:

```rust
// editor_game/menu_actions.rs:89-101
"Save" => { if let Err(e) = self.save_scene(ctx.world, ctx.assets) { ... } }
"Save As..." => { ... }
```

**Symptom:** File → Save while playing serializes the mid-simulation world over your authored scene. Permanently. (The Ctrl+S path is safe by accident — `shortcuts.rs:140-143` returns early during Playing.)

**Fix:** add the guard. One line each. Then decide whether Save-during-play should be disabled or should save the *snapshot* rather than the live world.

### 1.4 Inspector edits never mark the scene dirty

`panel_renderer/inspector.rs` contains **zero** `mark_dirty()` calls. `apply_component_edit` (`component_editors.rs:338-352`), `AddComponentCommand` (`inspector.rs:147`), and `RemoveComponentCommand` (`stored_component.rs:277`) all leave `is_dirty == false`.

And the "guard" on destructive actions is:

```rust
// editor_game/scene_io.rs:116-118
if self.editor.is_dirty() {
    log::warn!("Current scene has unsaved changes. Save first to avoid losing work.");
}
```
A log line. The world is cleared on the next statement.

Compounding: `EditorContext::title_bar_text()` (`context/mod.rs:398-402`) formats the `*` dirty indicator and **has zero callers**. Your window title reads "Insiculous Pong" — the game's config title. There is no way to know whether the scene is saved.

**Fix:** make `CommandHistory::execute`/`push_already_executed` the dirty source of truth — a command was recorded, therefore the scene changed. Render `title_bar_text()`. Then build a real confirm dialog (there is **no modal primitive anywhere in the editor** — this is a prerequisite for several later items).

---

### 1.5 Paused is editable and Stop discards the edits with no warning

`crates/editor/CLAUDE.md:67` states the design: `Paused` → editable. Every guard in the codebase tests `is_playing()`, not `in_play_session()`. Stop (`shortcuts.rs:78-102`) restores unconditionally. No dirty check, no prompt, no undo.

**Fix:** track "edited while paused" and either block it, or `status_bar.show_error` + confirm on Stop.

## 2. P0 — Three subsystems that are built and never called

These are why the editor looks less finished than it is. Each is written, tested, and unreachable from the frame loop.

> **Both confirmed by repro, 2026-08-27:** `G` does nothing visible, and the scroll wheel does not zoom.

### 2.1 The grid is never drawn

`grid.rs:135 generate_grid_sprites` and `:253 render_to_batcher` have **no callers outside `#[cfg(test)]`**. What the scene view actually does with the grid:

```rust
// panel_renderer/mod.rs:43-50
if editor.is_grid_visible() {
    ctx.ui.label_styled(&format!("Grid: {}px", editor.grid_size()), ...);
}
```

It prints the text `"Grid: 32px"`. That ghost string at the top-left of your viewport, half-covered by the toolbar, **is the grid feature**. `G` toggles a flag, the View menu shows a checkmark, prefs persist `grid_size: 32.0`, the LOD logic and red/green origin axes (`grid.rs:229-247, 269`) are all dead.

**Fix:** the grid is authored as world-space *sprites* but the scene view draws screen-space *UI*. Cheapest consistent path: rewrite as `ui.line()` calls in `render_scene_view`, iterating `visible_world_bounds()` through `viewport.world_to_screen`, clipped to bounds — matching how the collider overlay already works, and getting correct clipping for free.

> **Keep it square.** The deforming spring grid visible in the Pong play screenshot is a *game* render effect (the Geometry Wars look), not the editor grid. They are separate systems and should stay separate: the authoring grid is a square, axis-aligned, zoom-adaptive reference overlay with distinguished origin axes — its job is to make position and scale judgeable at a glance. `grid.rs` already implements exactly that (`calculate_lod_grid_size` at `:269`, red/green origin axes at `:229-247`); it just isn't called. Don't let the game's grid effect and the editor's reference grid converge — the moment the authoring grid deforms, it stops being a ruler.

### 2.2 The scroll wheel does nothing

```rust
// viewport.rs:125-143
pub fn zoom_at(&mut self, factor: f32, screen_pos: Vec2) {
    ...
    self.target_camera_zoom = new_zoom;
    ...
    self.target_camera_position += world_before - world_after;
}
```

Every write lands on `target_*`. The only code that moves `camera_*` toward `target_*` is `viewport.rs:160 update()`, reached via `EditorContext::update_viewport` (`context/mod.rs:434`) — **which has no callers**. `EditorGame::update` never calls it.

Zoom-to-cursor is correctly implemented and completely unreachable. Same root cause kills `reset_camera()` (Home), `pan()`, `focus_on()`, `focus_on_bounds()`.

**Fix:** call `self.editor.update_viewport(ctx.delta_time)` early in `EditorGame::update`. Then fix the frame-rate dependence at `viewport.rs:162` (`let t = self.interpolation_speed;` ignores `_delta_time`) — use `1.0 - (1.0 - speed).powf(dt * 60.0)`.

### 2.3 `F` (frame selected) is computed and discarded

`viewport_input.rs:152-155` sets `result.focus_requested = true`. **Never read** — `handle_viewport_picking` uses only `clicked`, `click_position`, `shift_held`, `ctrl_held`, and the marquee fields. `EditorContext::focus_on_selection` (`context/mod.rs:499`) has no callers, and delegates to a target-only method anyway (§2.2). `reset_requested` likewise unread. There is **no frame-all at all**.

**This is visible in your own screenshot.** In the Pong instance, the hierarchy lists 8 entities and the viewport shows one ball glow — the paddles and walls are off-screen. With `F` dead, zoom dead, and Home dead, the only recovery is middle-drag panning until you find them.

**Fix:** consume `focus_requested`; build positions from `build_pickable_entities`; call `focus_on_bounds` after §2.2 lands. Add frame-all on Shift+F.

## 3. P1 — The inspector

The 08:29 screenshot is the single most damning image in the set. Everything below is visible in it.

### 3.1 Label collision — labels overlap their input boxes

"Linear Damping" and "Angular Damping" run *into* their fields; "Angular Damping" is clipped mid-word by the input rectangle. Cause: `EditableFieldStyle` uses a fixed `label_width` with no measurement, so any label longer than the budget overruns.

**Fix:** measure the widest label in the component block and lay the column to that, or right-align labels to a fixed gutter and ellipsize. Same pass should fix the `[X]` button, whose position is `x + style.label_width + 90.0` (`editable_inspector.rs:337`, duplicated at `component_editors.rs:366`) — a magic offset that doesn't track panel width, which is why the X buttons float unaligned in the middle of the panel instead of sitting on the component header.

### 3.2 Axis letters render underneath their fields

The tiny red `X` / gray `Y` on Position, Scale, Offset, Velocity all sit on top of or behind the input boxes rather than beside them. The RGBA block is worse: R/G on one row, B/A on the next, columns not aligned, letters colliding with boxes.

**Fix:** treat a Vec2 row as one composite widget with its own internal layout (label gutter | X badge | field | Y badge | field), not four independently-positioned draws.

### 3.3 Inspector doesn't scroll — `+ Add Component` is unreachable

`grep -rn "scroll"` finds offsets only in `asset_browser.rs:44-45` and camera zoom. The inspector walks `y` downward inside a hard clip rect (`editor_game/mod.rs:151`). In your screenshot, Collider's `Radius` field is cut off at the panel edge with no scrollbar — and `+ Add Component` (`panel_renderer/inspector.rs:106-108`) is below that, permanently unclickable on any entity with four components.

Worse: the Add-Component *popup* is drawn at the same running `y` inside the same clip rect (`inspector.rs:104-121`) and does not use `begin_overlay`. Even if you could click the button, the popup would be scissored away.

**Same bug in the hierarchy** — `hierarchy.rs:131-134` lays out from a fixed origin and `render_node:152-164` culls rows outside bounds while still advancing `y`. Past ~30 entities, entities are invisible and unselectable. Pong has 8; a real game won't.

**Fix:** hoist `AssetBrowserState`'s scroll pattern into a shared `ScrollState`, give it to both panels. ~30 lines. Route the popup through `begin_overlay` and make it flip up when it would overflow.

### 3.4 Fake headers — sub-properties look like components

`inspector.header("  Shape: Circle")` (`component_editors.rs:208`) and `inspector.header(&format!("  Type: {}", type_str))` (`:157`) use the component-header style with two leading spaces as the indentation mechanism. In the screenshot, "Type: Dynamic" and "Shape: Circle" are visually indistinguishable from "RigidBody" and "Collider".

They're also **read-only** — you cannot switch Dynamic↔Static or change a collider's shape in the editor. Comment at `:151`: *"read-only for now - would need dropdown widget."* **The widget exists**: `EditableInspector::cycle` (`editable_inspector.rs:455-503`) already drives `UiAnchor` and the `Behavior` variant selector.

**Fix:** style sub-properties as a distinct tier; wire `cycle` to `RigidBodyType` and `ColliderShape`.

### 3.5 Hostile numeric fields

Every numeric field is a text box (`editable_inspector.rs:29-38`). Missing, relative to Unity/Godot/Blender and to your own `IdealEditor.png`:

- **No drag-to-scrub.** The most-used gesture in any editor. Tellingly, `EditableFieldStyle` still carries `slider_height: 16.0` (`field_style.rs:55`) that nothing reads, and the commands layer has merge machinery built *for* scrubbing (`commands/mod.rs:144-156`, `ComponentEdit::field_hint`) that only gizmo drags exercise.
- **No arrow-key increment, no steppers, no shift/ctrl precision modifiers.**
- **Rotation is in radians with no unit label**, clamped to `-PI..=PI` (`component_editors.rs:30-31`) — the field physically cannot express a rotation past 180°. `IdealEditor.png` says `Rotation: 0.0°`.
- **Silent clamping.** `POSITION: -1000.0..=1000.0` is a hard cap on world size typed into the inspector. Type 1500, get 1000, no message.
- **The inspector lies about values on disk.** `edit_normalized_f32` (`editable_inspector.rs:56-59`) clamps to 0–1 *for display*, compares the new value against the clamped one, and returns `Unchanged` — so a scene with `friction: 2.0` shows "1.0" while the world holds 2.0. Applied to `linear_damping`/`angular_damping` too, which are not 0–1 quantities in rapier.
- **No invalid state.** `EditResult` has exactly two variants (`field_style.rs:145-150`): `Unchanged`, `Changed`. A parse failure is structurally indistinguishable from "user typed nothing".
- **No monospace face**, so digit columns jitter as you drag. This is why `vec2_input_width: 70.0` is a fixed pixel guess.

**Fix, in value order:** drag-to-scrub in `ui::float_input` (one widget change lights up every field in the editor) → degrees at the boundary with a `°` suffix → soft ranges (clamp the scrub, allow typed values outside, warn) → `EditResult::Invalid` + red border → mono face.

### 3.6 Read-only islands, and one that blocks gameplay entirely

**Editable (9):** `Transform2D`, `Sprite`, `RigidBody`, `Collider`, `AudioSource`, `Behavior`, `UiLabel`, `UiPanel`, `UiButton`.
**Display-only (5):** `Camera`, `SpriteAnimation`, `Tilemap`, `AudioListener`, `EntityTag` — the `{ readonly }` specs at `stored_component.rs:319, 321, 322, 326, 328`. Note `Create Camera` is a first-class menu item (`menu/mod.rs:232`) for a component you then can't adjust.

The sharp one: **every `Behavior` string field is read-only** (`behavior_editor.rs:78, 85, 88, 99, 141, 144, 161, 180` all use `inspector.string`, which is display-only). `FollowTagged`, `ChaseTagged`, and `CameraFollow` all target entities *by tag string*, and `EntityTag` is `{ readonly }` too. **The tag is unwritable on both ends — tag-based gameplay cannot be wired up in this editor at all.**

The stated reason is stale:

> `behavior_editor.rs:7-9` — *"String fields (tags, target names) are read-only for now — the ui crate has no general text-input widget yet"*

`EditableInspector::string_edit` exists at `editable_inspector.rs:440-452` and `ui_component_editors.rs:46, 131, 135` already uses it in production. The blocker was removed and this file wasn't revisited.

**Fix:** swap eight `inspector.string` → `inspector.string_edit`. ~30 minutes. Delete the stale doc comment.

## 4. P1 — Everything else, grouped

### 4.1 Chrome bleed — game UI draws on editor chrome

Visible in three of six screenshots:
- Editor Demo in Play: an opaque game slider panel covers File/Edit/View and the top five hierarchy rows; `"HELLO WORLD"` renders in the menu-bar band; `"L cycles language"` collides with `v0.1.0` in the status bar.
- Pong in Play: `"YOU 0 - 1 CPU"` renders over the `Scene` panel title.

Root cause is §4.2: the game renders to the whole window and relies on opaque chrome to hide the overspill.

```rust
// dock/render.rs:96-100
// Draw panel background (skip for scene view — it shows game content directly).
// Uses the opaque EditorTheme background so game sprites never bleed through.
```

That's curtains, not clipping — and it doesn't cover the menu bar or status bar bands at all.

### 4.2 No viewport scissor — the game shades the entire window

`EditorGame::render` (`editor_game/mod.rs:340-349`) unconditionally overwrites the camera with `to_window_render_camera(ctx.window_size)`, rendering the world across the full window. In your Pong screenshot the game is shaded at 1040×790 and visible at ~545×470 — **3× the fragments needed**, with heavy additive glow overdraw.

**Fix:** set a scissor rect on the sprite pass equal to `scene_view_bounds()`. Fixes chrome bleed and the overdraw in one change.

### 4.3 Shared camera — a game cannot zoom

There is exactly one camera. During Play, the game camera is demoted to a position feed (`mod.rs:108-115`) and zoom is forced to 1.0 (`shortcuts.rs:52-56`, comment: *"the game's own camera has no zoom source"*).

Consequences: any camera-zoom gameplay is impossible under the editor and behaves differently outside it; editing pan/zoom is clobbered on Play and restored on Stop; you can't frame a distant entity while the game runs, which is the main reason editors keep two cameras.

The upside — `to_window_render_camera` guarantees overlay and GPU agree, locked by three tests (`viewport.rs:461-502`) — is worth keeping. **Fix:** two cameras; derive the render camera from whichever is authoritative for the play state; drive the overlay's `world_to_screen` from that same camera so picking stays truthful. **This one needs a design conversation, not a patch.**

### 4.4 No selection affordance in the viewport

No outline, no bounds box, no tint, no handles. `theme.selection_fill` is used only for hierarchy row backgrounds. The only viewport feedback is indirect:

```rust
// collider_overlay.rs:153-155
let is_selected = selection.contains(entity);
let width = if is_selected { OUTLINE_WIDTH_SELECTED } else { OUTLINE_WIDTH };
```

An entity is visibly selected **only if it has a `Collider`** and the overlay is on. Plain sprites — backgrounds, UI, decorations, most of a 2D scene — get nothing. Visible in your 08:29 shot: Ball is selected in the hierarchy and the inspector is full of its data, and the viewport gives you nothing.

There is also **no hover feedback** anywhere in the viewport.

**Fix (~25 lines, highest perceived-quality-per-line change in the codebase):** in `render_scene_view`, iterate `selection.selected()`, compute size the same way `build_pickable_entities` does (`viewport_interaction.rs:288`), map four corners through `world_to_screen`, draw four `ui.line`s with a new `theme.selection_outline`. Primary brighter than secondary. Then run the same at 40% alpha for the hovered entity.

### 4.5 Gizmos

- **Off by default.** `EditorTool::default()` is `Select` → `GizmoMode::None` (`context/mod.rs:157-163`) → nothing draws. Note `GizmoMode::default()` is `Translate` — the two defaults disagree. Combined with §1.1 (the toolbar click that would fix it clears your selection), the gizmo is reachable only by: click in hierarchy → press `W`. Nothing teaches that.
- **Rotate ring is a solid 148×148 square** (`gizmo.rs:375-382`) — `ui.interact` on a filled rect, not an annulus. Any click within 74px of the entity starts a rotation drag; you cannot click-select through it. No angle snapping, no numeric readout.
- **Scale's `still_dragging` uses the wrong rect** (`gizmo.rs:482-486`): every corner re-registers its widget id with `centered_handle_rect(screen_pos)` — the *center* handle. The correct rect is in scope four lines up. The scale tool breaks one frame into the drag.
- **Scale delta is additive raw screen pixels** with no zoom compensation (`gizmo.rs:476`). Should be multiplicative off drag-start scale.
- **Unclipped.** `handle_gizmo` runs after `render_panels` has popped every clip rect and only checks that the scene panel *exists* (`viewport_interaction.rs:154`). Pan an entity off the left edge and its handles draw over the hierarchy and remain click-draggable there. The collider overlay does this correctly (`collider_overlay.rs:148`); the gizmo doesn't.
- **Primary-only.** Multi-select then drag moves one entity.
- **`Gizmo::cancel()` exists (`gizmo.rs:497`) with zero callers** — Escape can't abort a mis-drag.

### 4.6 Snapping is unreachable, and broken if you reach it

`toggle_snap_to_grid` (`context/mod.rs:271`) has **no callers**. No menu item, no keyboard handler, no toolbar button. `EditorAction::ToggleSnap` is bound to bare `KeyS` (`editor_input.rs:174`) and never queried. The only way to enable snap is hand-editing `editor_prefs.json`.

And when enabled it eats the drag residual:

```rust
// viewport_interaction.rs:184-189
transform.position += world_delta;
if snap_enabled { transform.position = self.editor.snap_position(transform.position); }
```

The snapped value is written back into the authoritative position every frame. With `grid_size = 32` and a 2px/frame drag, `snap(p + 2.0) == p` every frame — **the entity never moves** unless a single frame's delta exceeds 16 world units.

**Fix:** hold the unsnapped position in drag state; snap only for display/commit. Add a View-menu toggle and a hold-to-snap modifier so it isn't a mode.

### 4.7 Marquee select is invisible

`SelectionRect::to_sprite` (`picking.rs:343`) and `to_border_sprite` (`:364`) have zero callers; `SelectionRect` is never instantiated in production. The consumer acts only on the release frame — during the entire drag, nothing renders.

Two more defects in that condition (`viewport_interaction.rs:77-89`): `selection_start != Vec2::ZERO` is a sentinel, so a marquee starting exactly at screen (0,0) is silently dropped; and `ctrl_held` is ignored, so Ctrl+drag destructively replaces instead of toggling.

### 4.8 Picking

- **Unrotated AABB in world space** (`picking.rs:196`) — `global_t.rotation` is dropped. A 45°-rotated sprite has a hit box ~41% too large on the diagonals and misses its own corners.
- **Sprites only** (`viewport_interaction.rs:279`). Cameras, empties, colliders-without-sprites, UI elements are unclickable — hierarchy-only.
- **`pick_margin: 2.0` is in world units** (`picking.rs:154`). At zoom 0.1 that's 0.2 screen pixels; at zoom 10 it's 20. Should be `px / camera_zoom`.
- **Equal-depth ties resolve nondeterministically.** Sort is descending on `sprite.depth` (`picking.rs:203`) with ties falling back to `world.query_entities` order — and the ECS is HashMap-backed. Add `entity_id` as a stable secondary key.
- **`reset_cycle` (`picking.rs:271`) has no callers**, so cycle state never resets on selection change, and `last_pick_pos` is polluted by the asset-drop path (`viewport_interaction.rs:110-114`).

### 4.9 Two competing shortcut systems, one dead

`EditorInputMapping` (`editor_input.rs`) defines 22 actions with a rebinding API. **Two** are ever queried (`FocusSelection`, `ResetCamera`) and both outcomes are discarded (§2.2, §2.3). The real shortcuts are hardcoded `KeyCode` matches in `shortcuts.rs`.

The dead bindings are also wrong as written: `Duplicate → KeyD  // Ctrl+D`, `Undo → KeyZ  // Ctrl+Z` — bare keys with the modifier only in a comment. `InputSource` has no chord representation. If anything ever queried these, bare `D` would duplicate.

**Fix:** pick one. Extending `InputSource` with chords and routing `handle_editor_key` through the mapping buys you the rebinding UI the module was clearly written for. Shipping both is how `F` and `Home` ended up silently broken.

**Missing vs. convention:** arrow-key nudge (+Shift 10×) — there is *no* precise-placement path except typing into the inspector, and typing is clamped (§3.5); frame-all; Escape-cancels-drag; Escape-deselects; Ctrl+A; Ctrl+C/V/X (menu items exist, enabled, and hit `_ => log::info!("Unhandled action")`); hold-modifier axis constraint; right-click context menu anywhere (RMB is entirely unused in the viewport).

### 4.10 Hierarchy

Present: nesting with indent, expand/collapse, single-click select, Ctrl-click toggle.
**Absent:** scrolling (§3.3), rename, search/filter, drag-to-reparent (`DragPayload` has one variant: `Texture`), sibling reorder (order is `sort_by_key(EntityId)` — not authored, not persisted), visibility toggle, lock, right-click context menu, type icons, a scene root node.

**And `Name` is unreachable.** It exists, and the hierarchy already prefers it (`hierarchy.rs:84-102`) — which is why your fresh screenshots read "Left Paddle" and "Ball" instead of "Sprite (Entity 1)". But it's filed under `hidden:` in the registry (`stored_component.rs:312`), meaning "captured for undo only, never inspected". So it's excluded from `ComponentKind`, from Add Component, from `edit_all_components`. **You can never rename an entity.** Entities created by game code rather than editor actions fall through to the type-name fallback and can't be fixed.

**Fix (mechanical, high value):** move `Name` from `hidden:` to `builtin:` with `{ edit edit_name => SetNameCommand }`; write `edit_name` with the existing `string_edit`; add `SetNameCommand`; add F2/double-click rename in `render_node`.

**Also observed:** hierarchy order changes during play. In the 08:17 Pong shot the order is Background, Left Paddle, Right Paddle, Ball, Top Wall…; in the 08:18 shot after play, Ball has moved to the bottom (recreated with a higher EntityId). Any UI that assumes stable row indices will misbehave.

### 4.11 Selection model

`Selection` is genuinely multi (`HashSet` + `primary`), and both entry points feed it. Every consumer reads `primary()` only — inspector, gizmo, duplicate. Only delete honors the full set.

And `primary` is chosen nondeterministically:

```rust
// selection.rs:94-98
self.primary = self.selected.iter().next().copied();   // HashSet iteration order
```

Rubber-band five entities, and the inspector shows an arbitrary one — a different one across runs. There's no distinct styling for primary vs. secondary, so nothing tells you which of the five you're editing.

**Fix:** `IndexSet`/`Vec` for `selected` so ordering is insertion-stable — cheapest possible fix, do it today. Then primary styling, gizmo-on-set-with-primary-as-pivot, shift-click range select.

### 4.12 Undo — the silent holes

Undoable: create, delete, duplicate (top-level), add/remove component, inspector field edits, gizmo transforms, texture drop.

**Bypassing the command system:**
- **Duplicate loses its children on undo.** `duplicate_entity_recursive` (`entity_ops.rs:282-332`) directly creates the whole subtree with no commands; the caller records **one** command for **one** entity (`menu_actions.rs:156-161`). Verify `CreateEntityCommand::already_created` walks descendants — if not, Ctrl+D then Ctrl+Z orphans every child into the world and into the saved scene.
- **Ctrl+Z mid-gizmo-drag.** `handle_editor_key` (`shortcuts.rs:146`) doesn't check `gizmo_has_priority()`. Undo fires against the previous command while the drag keeps writing; the drag's release-command then captures post-undo state as its "final". Tracked as `GPP-L7 (Low, document-only)` in `crates/editor/TECH_DEBT.md` — it is not document-only.
- `Name` mutation on duplicate (`entity_ops.rs:306-309`) outside any command.

### 4.13 Absent: multi-edit, component copy/paste, prefabs, reset-to-default

All four absent, though three are nearly free given existing machinery: `ComponentKind::capture` returns a `StoredComponent` and `StoredComponent::apply_to` writes it back, so copy/paste-component is ~20 lines. `ComponentKind::add_default` already knows every default, so a "↺" per component header is nearly free.

"Prefabs" today are 9 hardcoded factory functions dispatched by **string match on menu labels** (`entity_ops.rs:149-160`, tracked as `ARCH-101`). A typo'd label fails silently into `None`. A user cannot author one.

## 5. P1 — Visual system

### 5.1 Settle the gamma question first

Backgrounds authored as `#1e1e1e` (30) measure **91** in the screenshots; `bg_header` at 0.12 measures 92. That's a linear→sRGB double-encode — colors authored as sRGB being treated as linear on output. **Verify the swapchain format and whether `Color::from_hex` linearizes.** Until that's settled every color decision is guesswork, and re-picking the palette before fixing it wastes the work.

### 5.2 No elevation model

```rust
bg_input:    Color::from_hex(0x2d2d2d),        // 45,45,45
bg_header:   Color::new(0.12, 0.12, 0.12, 1.0), // 30.6,30.6,30.6
```

| pair | ratio |
|---|---|
| header vs panel body | **1.01:1** |
| status bar vs panel | 1.04:1 |
| input vs panel | 1.21:1 |
| panel vs viewport | 1.26:1 |
| `border_subtle` on panel | 1.32:1 |

| selection fill vs panel | 2.01:1 |

`theme.rs:41` documents `bg_header` as *"darker than bg_primary"*. It is **lighter**, by 0.6/255. Six theme tests assert alpha and never luminance.

**Fix:** a real ladder — `surface_0` window/viewport, `surface_1` panel body, `surface_2` header/status, `surface_3` input/popup, `surface_4` floating + shadow. Add `#[test] fn adjacent_surfaces_are_distinguishable()` — you already have that discipline in `typography.rs:36`; the theme just lacks it.

### 5.3 Invisible popups

Every floating surface uses the same token as the panel behind it (`theme.rs:344 theme.panel.background = self.bg_primary`), drawn via `ui.panel` at `menu/mod.rs:397`, `panel_renderer/inspector.rs:121`, `toolbar.rs:133`. **Contrast between an open dropdown and its backdrop: 1.00:1.** Border 1.32:1. No shadow, no radius, no scrim. The dropdown isn't translucent — it's opaque and identically colored, so you see floating text with no container.

### 5.4 One implicit z-band

There is no z/layer concept. Draw order *is* layering, defined by statement order in `EditorGame::update:313-337`. The only escape hatch is `ui.begin_overlay`, used twice — and it's a single band, not a stack, so the drag ghost and an open dropdown share it.

**Fix:** `enum UiLayer { Content, PanelChrome, Floating, Modal, Tooltip, DragGhost }`, collect per layer, flush in order. Short of that, route *every* popup through `begin_overlay` and make popups position-aware. Right now the answer to "why is this behind that" is always "statement order", and that's not something you can build a modal dialog on — which §1.4 needs.

### 5.5 Panel titles are struck through

`HEADER_HEIGHT = 24.0` with a 14px face leaves descenders reaching ~y+22, and `draw_panel_chrome` paints the accent rule at exactly `y + height - 2` (`dock/render.rs:300-308`). **Fix:** 28px header for a 14px face, rule as a 1px `border_subtle` line outside the text box, ticks moved to the outer 4px or removed, clip + ellipsize.

### 5.6 The serif font is one line

## 6. The end state: authoring the game in the editor

### 6.1 Where game logic lives today

Three layers, one of which the editor can see.

`EditorGame<G: Game>` holds `inner: G` as an opaque value (`editor_game/mod.rs:34-63`) with exactly one call into it: `self.inner.update(ctx)` at `:181`, gated on `is_playing()`. Everything the editor knows about the game arrives through `&mut World`. **It can start and stop `update()`; it cannot enumerate, introspect, or attach to it.**

There is no system registry. Games hand-sequence their systems inside one monolithic `fn update` — `examples/editor_demo.rs:229-314` is the reference shape. Pong's rules are free functions in `../games/pong/src/*.rs`, and per `PROJECT_ROADMAP.md:407-409` game crates have **no editor dep**. So the rules are neither a registered system nor a discoverable trait impl — they're the body of one function in a crate the editor has never heard of.

The one data-driven slice is `ecs::behavior::Behavior`, a closed 8-variant enum. `behavior_editor.rs` is a complete, non-stub inspector for it — ~200 lines of hand-written per-variant editors. It is the *data-driven-behavior* case, not a script surface. Adding a behavior costs three crates: `ecs/src/behavior.rs`, `engine_core/src/scene_data.rs`, and that match. A game crate cannot do it at all — `Behavior` lives in `ecs`, upstream of everything.

### 6.2 Why a game component can't appear in Add Component today

Four independent blockers:

1. **Dependency direction.** `ComponentKind::ALL` is a `const` generated from macro input in the editor crate's own source (`stored_component.rs:203`). Game crates are downstream. `editor_integration/CLAUDE.md:18-22` pins the graph; no plugin or dylib edge exists.
2. **No runtime-typed path.** `add_default`, `capture`, `remove` are all `match self { ... }` over the compile-time variant set. Opening this needs `Box<dyn Fn(&mut World, EntityId)>` keyed by `TypeId` or name — a different mechanism, not a bigger macro.
3. **A second hand-maintained copy of the same list** in `WorldSnapshot` (§1.2), which destroys what it doesn't recognize.
4. **No wire format.** `ComponentData` is a closed enum in `engine_core`, upstream of every game, with no `Custom { type_name, data }` escape hatch. Tracked as `ARCH-006` (`PROJECT_ROADMAP.md:390`).

Worth knowing: **a real dynamic registry already exists and the editor doesn't use it.** `CLAUDE.md:34` names `crates/ecs/src/component_registry.rs` — `registry.register::<T>()` — and `README.md:176` names `#[derive(ComponentMeta)]` in `ecs_macros/`. Zero references to either appear anywhere in the editor or editor_integration sources.

### 6.3 The seam

A **`ScriptRef`**: a stable, serializable identity for a chunk of game logic, plus a runtime `ScriptRegistry` that resolves it to real Rust.

```rust
// crates/ecs/src/script.rs  (NEW — must live in ecs; editor depends on ecs and
// deliberately not on engine_core, per crates/editor/CLAUDE.md:4)
pub struct ScriptRef {
    pub script_id: String,                     // "pong::PaddleAi" — THE identity
    pub source_path: String,                   // "src/paddle_ai.rs" — for RustRover
    pub params: BTreeMap<String, ScriptValue>, // the inspector's model
}
pub enum ScriptValue { F32(f32), I32(i32), Bool(bool), Str(String),
                       Vec2(f32,f32), Entity(EntityId), Color([f32;4]) }
pub struct Scripts(pub Vec<ScriptRef>);        // ONE component, N scripts
```

```rust
// crates/engine_core/src/script_registry.rs  (NEW — beside behavior_runner.rs)
pub struct ScriptDescriptor {
    pub id: &'static str, pub display_name: &'static str,
    pub source_path: &'static str,   // from file!() at registration
    pub category: &'static str,
    pub params: &'static [ParamSpec],
    pub make: fn() -> Box<dyn ScriptBehavior>,
}
pub trait ScriptBehavior: Send {
    fn on_attach(&mut self, _e: EntityId, _w: &mut World) {}
    fn update(&mut self, e: EntityId, ctx: &mut ScriptContext);
    fn apply_params(&mut self, p: &BTreeMap<String, ScriptValue>);
}
```

The four requirements map directly: **(a)** `Scripts` is a normal component; **(b)** hierarchy synthesizes a row per `ScriptRef`, inspector renders a block per `ScriptRef`; **(c)** `params` + `ParamSpec` drive generic widgets — **no per-script Rust in the editor crate**, which is the entire point; **(d)** `source_path` opens in RustRover.

**Why `Vec<ScriptRef>` on one component, not one component per script:** the ECS is HashMap-per-type, so N script types would need N component types — the closed-world problem again. One component with a runtime-keyed vec is the only shape a downstream game crate can contribute to.

**Why a `String` id, not an enum:** all four closed enums that would otherwise be extended — `Behavior`, `ComponentKind`, `ComponentData`, `EntitySnapshot` — live upstream of every game crate. The seam must be string→HashMap at the component, the wire format, *and* the editor catalog, or it doesn't compose.

### 6.6 The decisions only you can make

1. **String-keyed runtime registry vs. more enums.** Not really optional — every closed enum is upstream of game crates. But decide it explicitly, because it invalidates the "add a variant" reflex the codebase currently rewards.
2. **Proc-macro reflection vs. manual descriptors.** Manual is explicit and greppable, matching `AGENTS.md:49` ("no hidden side effects, magic, or clever tricks") — but ~20 lines per script that will drift from the struct. Suggest manual in Stage 3, `#[derive(Script)]` at 3.5 once `ParamSpec` stops changing. **Note:** attribute parsing needs `syn` "full", which contradicts open debt item `KISS-001` (`PROJECT_ROADMAP.md:397`) — close or reclassify it first.
3. **Script-as-component vs. script-as-node — and note your sketch contradicts itself.** `IdealEditor.png` shows `PlayerController.cs` as a *child node* beside `Sprite2D` and `Collision` (Godot's model), while the *same image's* inspector shows Transform / Sprite Renderer / Physics 2D as stacked component blocks (Unity's model). The engine is unambiguously the second. **Suggest:** keep the component model, and make the hierarchy *display* scripts as pseudo-child-rows without them being real entities — that buys the sketch's look at Stage-2 cost. If they become real child entities, `duplicate_entity_recursive`, `DeleteEntityCommand`'s reparenting, and `build_pickable_entities` each need a filter.
4. **dylib hot-reload vs. build-and-relaunch.** Suggest relaunch. Three codebase-specific reasons dylib is a trap: `TypeId` is not stable across dylib reloads and the ECS is `TypeId`-keyed with a documented downcast footgun (`CLAUDE.md:53-56`) — storage corrupts on reload; panics unwinding across FFI are UB; and **wasm32 has no `dlopen`**, while `PROJECT_ROADMAP.md:222+` calls the WASM port "THE OPEN FRONT". Phase H actively forecloses the dylib plan. **Decide before Stage 3**, because it dictates whether `ScriptBehavior` may use `Box<dyn>` at all or must be `#[repr(C)] extern "C"`.
5. **Does the editor own the build?** Two incompatible entry points exist today. `run_game_with_editor` (`README.md:124-138`) puts the editor *inside* the game process, monomorphized over `G` — it can never rebuild the code it's running. The standalone binary (`cargo run --bin editor --features editor -- ../games/pong`) must instantiate *some* `Game` for an arbitrary directory. **`src/bin/editor.rs` is the single most important file for this question** — how it solves that today is the shape the scripting era should inherit. Resolve before Stage 5.
6. **Who runs the frame?** Engine-run scripts means a fixed phase order and games lose sequencing control (`editor_demo.rs:247-265` is hand-ordered today). Game-run means the editor's "attach script" UI can silently lie when a game never calls `ScriptRunner::update`. Suggest engine-run with a documented order, `Game::update` demoted to escape hatch — a real behavioral change for all shipped games.

### 6.7 What fights this end-state — change before building on it

1. **`WorldSnapshot`'s hardcoded list + `world.clear()`.** It *destroys* unknown components. **Fix before adding any game-defined data to entities.**
2. **Four parallel closed enums for one concept.** `ComponentKind`/`StoredComponent`, `ComponentData`, `Behavior`, `EntitySnapshot`. New types must be added to all four across three crates, and none can be extended downstream. `ARCH-006` names this for the scene format only — **widen it to all four and do it before the scripting phase, not "paired with" it.** The macro at `stored_component.rs:145-307` is genuinely good engineering for a closed set and precisely the wrong shape for an open one; its own doc ("add one line to that invocation") encodes the closed-world assumption.
3. **`EditorGame<G: Game>` is monomorphized over the concrete game.** The editor is a guest in the game's process with no seam at which it could hold logic at arm's length. Any hot-reload or editor-owned-build design must break this.
4. **Resource leakage is load-bearing, not an oversight.** `shortcuts.rs:95-96` explicitly relies on resources surviving `clear()`. Untangle before scripts start using resources, or script Play/Stop semantics will be unfixable.
5. **`Behavior` is the wrong thing to extend.** Both the docs and the registry make "add a variant" the path of least resistance, and each variant costs three crates and enlarges the eventual migration. **Freeze `Behavior` at 8 variants**; route new logic through the script seam; plan to reimplement the 8 as built-in scripts once Stage 3 lands, so there's one mechanism rather than two.
6. **`AssetKind` has no notion of source.** The test at `asset_browser.rs:163` asserts `.txt`/`.ttf` are ignored. The natural home for a script list can't see `.rs` at all.
7. **No confirm/discard dialog primitive exists anywhere.** A prerequisite for Stage 5, where losing work becomes routine — and for §1.4 today.

## 8. Should the editor run on the web?

Short answer: **yes, and it converges neatly with the `ScriptRef` seam — but web is the second-best way to make the editor AI-friendly, and it's worth being clear about which problem each solves.**

### 8.1 The case for it is stronger than it looks

- **Phase H already commits to WASM.** `PROJECT_ROADMAP.md:222+` calls the WASM port "THE OPEN FRONT". A web *editor* is mostly the same port plus an I/O backend — it isn't a new front, it's a deliverable of the one you're already opening.
- **It collapses two goals into one artifact.** You were already weighing building a showcase site for the first five games. A hosted editor makes the site *the* demo: "here's a game, and here's the editor it was built in, open it and move a paddle." For a portfolio piece that's a categorically better story than a screenshot.
- **It settles the dylib question by force.** wasm32 has no `dlopen`. Committing to web kills Stage 6 (§6.5) before it can eat months, which the analysis already recommends on independent grounds.
- **It's the only way an AI agent can currently touch the editor at all.** This session is the proof: I could read all 60 files of editor source and reason about every pixel of six screenshots, and I could not click a single button, because a winit window on your desktop is outside what any browser-based or file-based tool can reach. A web editor is inside it immediately.

### 8.2 The honest tension

The end state in §6 is *"author in the editor, edit Rust in a third-party IDE."* On the web there is no local filesystem and no RustRover. Two of the pieces in §6.4 don't survive the port as designed:

- **"Open in IDE"** (`Command::new(ide_cmd)`) has no web equivalent. Best available: an in-browser read-only source view, or a deep link to the file on GitHub.
- **"Build & Reload"** (Stage 5) needs a `cargo build`. On web that's a remote build service — a genuinely bigger project than everything else in this document combined.

**But the seam resolves most of this, and that's the interesting part.** If game logic is `script_id` + `params` (§6.3), then a web editor can attach scripts and tune every exposed parameter *without compiling anything* — the deployed WASM binary already contains every registered script. Scene authoring, entity placement, component tuning, behavior wiring, and parameter tuning all work fully in the browser. Only *writing new script bodies* needs a compiler.

So the split is clean and worth planning around explicitly:

| Capability | Native editor | Web editor |
|---|---|---|
| Scene authoring, place/transform/parent | ✅ | ✅ |
| Component add/remove/tune | ✅ | ✅ |
| Attach scripts, tune script params | ✅ | ✅ |
| Play / pause / step | ✅ | ✅ |
| Save/load scenes | filesystem | OPFS or File System Access API, plus import/export `.ron` |
| Author new script *source* | RustRover | read-only view, or GitHub deep link |
| Build & reload changed Rust | ✅ (Stage 5) | remote build service — defer |

That is not a crippled web editor. That's most of the job.

### 8.3 Where I'd push back

**"AI friendly" and "web" are related but not the same requirement, and web is the weaker of the two answers.**

Driving an editor by screenshots and pixel coordinates is the *worst* interface an AI can have to an authoring tool. It's slow, it's lossy, it can't verify its own work, and every UI change breaks it. If the goal is genuinely that AI assistants can build games in this engine, the higher-leverage move is a **text command/RPC layer** — the editor's actions exposed as a scriptable protocol:

```
select Ball
set Transform2D.position [0, 120]
add Collider circle radius=8
attach script pong::PaddleAi speed=240
save scenes/pong.ron
```

Note that **every one of those actions already exists as a `Command`** in `crates/editor/src/commands/`. The command system was built for undo, and undo-able-command is exactly the right granularity for a scriptable API — you'd be exposing something you already have, not designing something new. That layer:

- works identically native and web,
- gives an agent verifiable state (`describe entity Ball` returns the truth, no screenshot inference),
- makes the editor testable end-to-end without a display,
- and makes *the scene file itself* the AI's natural interface, which it already partly is — RON is readable and an agent can already edit it directly.

The honest framing: **the scene format is the AI interface, the command layer is the AI's write path, and the web editor is the human's demo surface and the agent's fallback.** All three are worth having. If you only do one, do the command layer — it's smaller, it composes with what exists, and it makes the other two better.

**§9 is the plan for it.**

### 8.4 Suggested roadmap placement

- **Now:** add "web editor" as an explicit deliverable of Phase H rather than a separate phase, and write down the native/web capability split above so §6.4's IDE and build pieces are designed as native-only from the start instead of being discovered as blockers later.
- **With §6 Stage 1:** design `ScriptRef` params to be fully editable without a compiler. This is already how it's specified — just make it a stated requirement so it doesn't drift.
- **Parallel, small:** the command/RPC layer over the existing `Command` types (§9). Doesn't depend on the web port and pays off immediately for testing.
- **Defer:** remote build service. It's the one piece here that's genuinely large, and the seam makes it unnecessary for most authoring work.

## 9. The command layer — an AI-friendly production path

§8.3 argues for this; this section is the plan. It's placed as a peer of §6 deliberately: **the script seam is how a game's logic becomes visible to the editor, and the command layer is how the editor becomes drivable by something that isn't a mouse.** They're independent and they compose.

### 9.1 Why this is the smallest high-leverage thing in the document

The pitch for the engine is AI-friendliness. Today the editor is the *one* surface an AI can't touch: an agent can read every line of the engine, edit `.ron` scenes directly, and drive `cargo` — but the authoring tool itself is a native window reachable only by pixels, and driving a UI by screenshot coordinates is slow, lossy, unverifiable, and broken by every layout change.

The fix isn't a new subsystem. It's exposing one you already built. `EditorCommand` (`commands/mod.rs:34-57`) is a reversible, world-mutating, mergeable action — which is *exactly* the granularity an external caller wants. `CommandHistory` already gives ordering, undo, redo, and coalescing.

Secondary payoffs that arrive with it, all of which you'd otherwise build separately:

- **Headless end-to-end tests.** Today `crates/editor` tests are unit-level because anything involving the frame loop needs a display. A command layer makes "create sprite, set position, save, reload, assert position" a plain test.
- **Reproducible bug reports.** A failing sequence is a text file, not a video.
- **A scripting/macro path for you**, not just for agents — batch renames, bulk retargeting, procedural level stamping.
- **The web editor's remote-control channel** (§8) falls out for free — same protocol over a WebSocket.

### 9.2 What already exists, and the three things that don't

**Exists and is reusable as-is:**

| Piece | Where |
|---|---|
| Reversible action abstraction | `EditorCommand` trait, `commands/mod.rs:34` |
| Ordering, undo/redo, history cap | `CommandHistory`, `:64-177` |
| Coalescing for continuous edits | `try_merge_or_execute` / `try_merge_or_push`, `:148-170` |
| Concrete commands | `Create`/`Delete`/`Macro` (`entity_commands.rs`), `Add`/`RemoveComponent` (`component_commands.rs`), 10 × `Set*Command` (`set_commands.rs`) |
| Entity factories | `entity_ops.rs` — 9 create functions |
| **Generic read path** | `inspect_all_components` (`stored_component.rs:287-305`) → `inspector.rs:64`, which already renders *any* `Serialize` component without per-type code |
| Scene save/load | `scene_io.rs` |

**Missing — and only three things:**

1. **Commands aren't addressable.** `EditorCommand` has `display_name()` — a human string for the Edit menu, not an identifier. Nothing maps `"set_transform"` → `Box<dyn EditorCommand>`. This is the §6.2 closed-world problem again, in a second place.
2. **Commands aren't constructible from data.** No serde on the command types, no parameter schema.
3. **There is no query API at all.** The read half is the half an agent needs most — it can't verify its own work without it. Crucially, **the mechanism already exists**: `inspect_all_components` walks an entity's components generically via serde. It's just being rendered to pixels instead of returned as data. Splitting "read entity state as a value" from "draw entity state as rows" is most of the work here, and it improves the inspector too (§5.8 notes `InspectorStyle`'s colors are dead because the read-only renderer bypasses them — same refactor).

### 9.3 Three convergences worth knowing before sequencing

These make the command layer cheaper than it looks, and make three other items on the list cheaper in return.

**a) It shares an insertion point with the dirty-tracking fix (§1.4).** The recommendation there is to make `CommandHistory::execute`/`push_already_executed` the source of truth for `is_dirty`. That is the same chokepoint the command layer routes through. Do them in one pass.

**b) It needs stable entity addressing, which is §4.10.** Commands take `EntityId`, which is not stable across sessions — and, as your own screenshots show, not even stable across a Play/Stop cycle (Ball moved to the bottom of the hierarchy after play, having been recreated with a higher id). An agent must address entities by `Name`. So **making `Name` editable isn't only a UX nicety — it's a prerequisite for this.** Same for a `find` query and for readable diffs.

**c) It is the natural test harness for §6.** Once scripts are `script_id` + `params` (§6.3), `attach script pong::PaddleAi speed=240` is a command like any other, and the whole scripting arc becomes testable without a display.

### 9.4 Shape

Keep the protocol boring. Line-oriented text in, JSON out — readable by a human in a log, trivially parseable by an agent, no schema negotiation.

```rust
// crates/editor/src/command_api/mod.rs  (NEW)

/// A command that can be named, described, and built from arguments.
pub trait CommandSpec {
    const ID: &'static str;                       // "set_component"
    fn describe() -> CommandDoc;                  // params + types, for discovery
    fn build(args: &Args, world: &World) -> Result<Box<dyn EditorCommand>, ApiError>;
}

/// Read-only questions. Never touches CommandHistory.
pub enum Query {
    ListEntities { filter: Option<String> },
    Describe { entity: EntityRef },               // → serde value per component
    Selection,
    SceneInfo,                                    // path, dirty, entity count
    ListCommands,                                 // self-describing: the agent's manual
}

/// Name-first, id as fallback. See §9.3(b).
pub enum EntityRef { Name(String), Id(u32) }
```

Discovery matters more than it sounds: `ListCommands` returning the `CommandDoc` set means an agent doesn't need documentation that can drift — the editor describes itself. That's the difference between a protocol an assistant can use reliably and one it guesses at.

### 9.5 Insertion points

| Piece | File | Change |
|---|---|---|
| Protocol types, dispatch, `Args` parsing | `crates/editor/src/command_api/mod.rs` **(NEW)** | Pure; no UI deps |
| `CommandSpec` impls | `crates/editor/src/command_api/specs.rs` **(NEW)** | One per existing command type. Mechanical — the `impl_set_component_command!` macro can emit these alongside the command |
| Query execution | `crates/editor/src/command_api/query.rs` **(NEW)** | Reuses `ComponentKind::capture` + serde |
| **Read-path split** | `inspector.rs:64`, `stored_component.rs:287-305` | Extract `inspect_all_components` into "produce values" + "render values". The renderer becomes a consumer of the same data the API returns |
| Entity addressing | `hierarchy.rs:84-102` `entity_display_name` | Add the inverse: `resolve_by_name(world, &str) -> Option<EntityId>`, with ambiguity as an error rather than a silent first-match |

| Session hook | `editor_game/mod.rs` `EditorGame::update` | Drain a pending-command queue at a defined point in the frame — **before** `render_panels`, and **skipped while `gizmo_has_priority()`**, so an API write can't interleave with a live drag (§4.12's `GPP-L7` bug is the same hazard) |
| Transport | `crates/editor/src/command_api/transport.rs` **(NEW)** | Stdin/stdout first. A Unix socket or WebSocket later, behind the same dispatch |
| Native binary flag | `src/bin/editor.rs` | `--api` for headless/attached operation. Note this file is also the §6.6(5) open question — worth resolving both at once |

### 9.6 Stages

**Stage A — days. Query only. Read-only, zero risk.** *Cheap.*
The read-path split, `EntityRef` resolution, `ListEntities` / `Describe` / `Selection` / `SceneInfo`, stdin/stdout transport. **Ship point:** an agent (or you, or a test) can ask the running editor what's in the scene and get structured truth back. Nothing can be broken by it, and it immediately makes every subsequent stage verifiable.

**Stage B — days. Write, over existing commands.** *Cheap-to-moderate.*
`CommandSpec` for the commands that already exist; dispatch through `CommandHistory`; `undo`/`redo`/`save` as API verbs; `ListCommands` discovery. **Ship point:** a text script can build a scene, and every step is undoable in the GUI exactly as if you'd clicked it.

**Stage C — days. Headless mode.** *Moderate.*
`--api` without a window. Depends on how tightly `EditorGame` is bound to the frame loop and the `ui` context — the honest unknown here, and worth a spike before committing. **Ship point:** end-to-end editor tests in CI, and scene generation without a display.

**Stage D — small, later. Web transport.** Same dispatch over a WebSocket once §8 lands. Effectively free at that point.

### 9.7 Decisions

1. **Text protocol vs. JSON-RPC.** Suggest line-oriented text in / JSON out for Stage A–B: an agent writes it fluently, a human reads it in a log, and it needs no client library. Move to JSON-RPC only if you want IDE integration.
2. **Does the API go through `CommandHistory` or around it?** Through, always. An API write that isn't undoable is a trap — you'd discover it the first time an agent does something wrong and you can't Ctrl+Z it. The cost is that bulk operations flood the history; `MacroCommand` (`entity_commands.rs`) already solves that, so expose an explicit `begin`/`end` batch.
3. **Name collisions.** Nothing enforces `Name` uniqueness today (`entity_ops.rs:32` appends a counter, but game-created entities bypass it entirely). Decide: unique-enforced, or `find`-returns-many and commands take a resolved id. Suggest the latter — cheaper, and honest about ambiguity.
4. **In-process or out-of-process.** Stage A–C are in-process (the API drains inside `EditorGame::update`). That keeps world access single-threaded and avoids every synchronization question. Don't reach for a background thread unless something forces it.
5. **Does this replace the GUI's own paths, or sit beside them?** Beside, at first. But the long-term win is if GUI actions and API actions both funnel through `CommandSpec` — then the API can never drift behind the GUI, and "what can the editor do" has exactly one answer. Worth deciding early even if you implement it gradually, because retrofitting is what produced the two competing shortcut systems in §4.9.
