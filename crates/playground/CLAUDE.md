# playground — Crate Guide

The editor in the browser: a `cdylib` + `rlib` that boots the editor over `ProjectHost`
on wasm32, keeps the open project in IndexedDB, and exposes the command API and a file
interface to the page as `wasm_bindgen` functions. Everything that can run natively is
target-agnostic and unit-tested natively; the wasm-only files are the thin layer and are
compiled by `scripts/check_wasm.sh`. The contract is `docs/WEB_PLAYGROUND.md`.

## Dependency graph
```
playground ──→ editor_integration, editor, engine_core, audio, music_midi, common   (+ the wasm bridge family on wasm32 only)
```
No crate depends on `playground`. It is the only workspace member that pulls the editor
crates into the wasm gate.

## File Map
- `lib.rs` — module list; `web_entry` is wasm-only.
- `web_entry.rs` (wasm) — `ASSET_BASE`, `BUNDLE_VERSION` (the five-place version contract in the header), boot order: `?mode=preview` returns to `preview_entry` before anything else; otherwise logging → preload → open the store (memory fallback + banner) → sweep orphans → manifests → pick the project from `?project=` → load stored files onto `MemFs` (a tombstone's bytes never; its path dropped, the bundled copy with it) → seed the chains (tombstones included) → the write and remove observers + listeners → bridge channels → dispatch `playground-ready` → the hidden-frame pump (the preview window hides this tab, and the snapshot must still be answered) → `run_game_with_editor_opts`.
- `bridge.rs` — the `playground_*` exports and the pure rules behind them (`validate_bridge_path`, `can_dispatch`, `dirty_or`); the internal `live_scene(generation)` behind `playground_snapshot` and the live-scene `playground_export_zip`; `Hooks` for `source_check` / `script_errors` / `scene_snapshot` / `preview_open` / `open_song` / `song_import`; `playground_write_file_bytes` and `playground_sample_references`, the file import's two exports over `upload.rs`. `playground_poll_file_changes` drains the separate file-change queue fed by the write and remove observers (both ends of a rename), deduplicated per poll and project-relative; `bridge/tests.rs` pins that it leaves the command FIFO untouched.
- `bridge/files.rs` (it translates editor asset-relative paths to the project-relative `assets/…` paths used by file reads, lists and the Scripts panel) — `playground_set_file_mutation_guard` stores the page callback; the editor's run-option guard calls it synchronously with project-relative `removed` and `renamed` paths and `prepare` / `done` / `failed`. A nonempty return refuses before mutation; the outcome releases the Scripts panel's save block, and only `done` moves its save target.
- `upload.rs` — the file import: `plan_upload` (the name rule, the loader's byte limit before any decode, the loader itself; a song is any name `editor::external_tools::is_midi_path` accepts), `import_file` (the destination by kind, a taken name answered unwritten unless replaced, a replaced song's sidecar kept — the score changed outside, which the song follows with its map and the track diff's lines, at its next open or, for the Conductor panel's open song, at once: `open_song_replaced` says so and the bridge files the bytes in the editor's `song_import` mailbox; `sidecar_lost` says the score changes and the map is kept), `songs_referencing` (every sidecar by `sidecar_midi_path`); `upload/tests.rs`.
- `store.rs` — `ProjectStore` (the CAS `put`, and `remove_file`, which takes a manifest, writes a tombstone through the same CAS put and returns the new revision), `StoredFile` (`deleted` marks a tombstone), `StoreError`, `Fut`.
- `store/directory.rs` — native test double, lock file per project.
- `store/memory.rs` — every target; the fallback when IndexedDB will not open. Its test-only `fail_after` hook fails one mutation at a chosen durable boundary.
- `store/indexed_db/{mod,cursors}.rs` (wasm) — database `beinsiculous.playground` v1, stores `files` and `projects`; the CAS `put` and `remove_file`.
- `store/idb_transaction.rs` (wasm) — the transaction-to-future adapter; the only place web-sys IndexedDB verbosity lives.
- `persist/mod.rs` — `Chains`: what the store holds per path (`PathChain`), the five path states, `is_pending` vs `has_active`, the DOM banner; the wasm driver and listeners.
- `persist/queue.rs` — the one FIFO of puts and removals in write order: `on_vfs_write`, `on_vfs_remove` (a bundled-only path gets a revision-zero chain), `poll_head`, `handle_completion`, the head-of-line retry. Removal uses the store's returned revision, so a recreate queues above its own tombstone without reseeding.
- `persist/tests/` — `mod.rs` (the gated store, the pong-chains helpers), `chains.rs` (hand-polled state-machine tests), `queue.rs` (write order, removals, tombstones), `mutations.rs` (bundled-only deletion and folder rename through the observers, reloading each durable boundary), `song_saves.rs` (a song's save — each final through its temporary file — reopened after every operation), and `stores.rs` (native directory double tests).
- `projects.rs` — `ProjectManifest`, `ProjectEntry`, `list_projects` (pure merge), `validate_slug`, the computed project root.
- `archive.rs` — target-agnostic project zip export and import validation (`collect_asset_entries` + `write_archive` behind `export_project` and `export_snapshot`, which splices the live scene and the open song's live files over the saved ones, every other file carried unchanged); `archive/songs.rs` (step 14: a song file that fails refuses the archive; a `.new` an older project left is any other file); `archive/tests.rs`, `archive/song_tests.rs`.
- `preview.rs` — target-agnostic: `unpack_preview` (the importer's refusals plus `MissingScene`) and `preview_state`, the rule behind the page's readiness question (a scene error, then the boot status by phase: progress before the first frame, terminal after it).
- `preview_entry.rs` (wasm) — the `?mode=preview` runtime: `announce_preview_mode` and the four `playground_preview_*` / `playground_load_preview` exports. No store, no chains, no bridge, no preload.
- `assets/projects/pong/` — bundled project: pong scene (`scenes/pong.scene.ron`), paddle/ball textures, and gameplay scripts (`scripts/{paddle,ball,goal,scoreboard}.rhai`).

## Godot Oracle
Godot keeps projects on a real filesystem; the closest reference is `editor/editor_file_system.cpp`
for scan/refresh semantics. The CAS-per-file design has no Godot analogue.
